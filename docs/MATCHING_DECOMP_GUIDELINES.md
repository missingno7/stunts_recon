# Matching Decompilation: Operating Guidelines

**Objective:** maximize verified source recovery per unit of total model cost—not runnable approximations, attempt counts, or attractive progress reports.

Use these principles when establishing a worker's task and environment; do not reload both documents on every attempt. Open the [cookbook](MATCHING_DECOMP_COOKBOOK.md) only for the relevant procedure or evidence. These guidelines do not authorize bypassing a repository's acceptance, budget, or write controls. Repository evidence may qualify a recommendation; record the counterexample rather than forcing compliance.

## Facts and scope

- **The published Luna text-token rates checked on 2026-09-23 were 100× lower than Astra's for the same billing category and service/context tier.** This dated observation is not a permanent pricing rule or a claim about task cost, success rate, or ChatGPT/Codex subscription consumption. Both supervisor input and output matter; see [pricing and accounting](MATCHING_DECOMP_COOKBOOK.md#pricing-and-accounting).
- **Exactness has a scope.** A matched function is not a matched object, a linked image is not necessarily a historical link, and an exact hybrid containing raw oracle-owned regions is not complete source recovery. Binary identity does not establish unique original source text or correctness of a later port. [Evidence](MATCHING_DECOMP_COOKBOOK.md#evidence-and-sources)

## Operating principles

1. **Recover the original; do not invent a runnable replacement.** No placeholder graphics, guessed gameplay, synthetic success returns, silent no-ops, or omitted behavior to improve code size. Keep evidence-backed incomplete candidates; label gaps explicitly. Separate structural test scaffolds and later ports from the recovered game.

2. **Keep proof independent of search.** The worker proposes; the trusted build and verifier decide. Never manufacture a pass with copied executable code, byte patches, trimmed contributions, arbitrary padding, relaxed relocation checks, or a changed oracle. Verifier changes need separate review and negative tests. Authentic ASM and pinned historical libraries are legitimate, separately evidenced categories—not escape routes after failed C attempts.

3. **Define the actual compilation problem first.** Identify the oracle range, complete emitted extent, compiler/profile, ABI, declarations, data, fixups, and relevant object/TU context. A TU is a translation unit compiled together. Keep proven facts, supported hypotheses, and unknowns distinct. Do not convert inferred boundaries or names into unquestioned build constraints.

4. **Investigate the environment before blaming the source.** Pin tools and dependencies, isolate temporary files, and verify repeatability. Reduce suspicious failures to small fixtures; cross-check another runner when warranted. A compiler crash, unsupported binder, stale report, or emulator fault is not a failed source hypothesis.

5. **Use diagnostics as observations, not verdicts.** Similar size, matching call counts, a first differing byte, or a register correspondence does not establish the cause. Follow control flow, operand widths, data references, and relocation targets. Recover missing structure before tuning allocation; a DWARF name does not justify invented behavior.

6. **Choose experiments that distinguish hypotheses.** Record the observation, predicted machine-level effect, and falsifier before compiling. Deduplicate effective code/data/fixup results under the same relevant inputs—not merely source spelling or debug-sensitive object hashes. Identical output can disprove a distinction once; repeating it without a new question is waste.

7. **Escalate the analysis level before automatically escalating the model.** Source shape, types, lifetime, ABI, callers, object grouping, compiler state, and linking are possible investigation levels, not a rigid ladder. Do not preserve an accidental local match by retaining fake neighbors or manipulating optimizer state. Test coupled corrections in isolation and integrate them as a verified transaction.

8. **Do not confuse constrained workers with incapable models.** `SUPERVISOR`, a three-attempt cutoff, missing tools, and denied access describe the workflow—not Luna's intelligence. Compare models with comparable evidence, permissions, and budgets. When Astra succeeds, identify which additional resource enabled it and whether Luna could use the same advantage.

9. **Give cheap workers meaningful autonomy, not unlimited retries.** Default to Luna/high for bounded recovery and research where the environment supports it. Let workers inspect relevant evidence, design probes, and change hypotheses without per-attempt supervision. Distinguish hard shared ceilings from initial per-case allocations, and state who may reallocate unused slots. An available shared budget must not silently become an exhausted per-case limit. Use explicit cost limits and observed stagnation to tune budgets; change existing controls through reviewed policy, never by bypassing them.

10. **Script deterministic repetition.** Compilation, binding, comparisons, candidate enumeration, deduplication, status, and accounting belong in tools where practical. When an agent repeatedly performs the same manual procedure, automate it or delegate it cheaply. Build the smallest useful tool; a new framework must repay its maintenance and context cost through real recovery work.

11. **Optimize context density, not starvation.** Supply a bounded task, necessary source/evidence, reproducible commands, prior negatives, and the actual decision to make. Keep full artifacts accessible on demand. Remove duplicate history and tool-schema noise—not uncertainty, contradictory evidence, types, or constants needed for correctness. Measure actual request usage, not file size alone.

12. **Cheap work must not become expensive supervisor reading.** Workers archive detailed evidence themselves and return a compact result, proof scope, remaining blocker, artifact references, and precise question. No chronological transcript by default. Supervisors return short, high-leverage decisions; successful routine work should not require a model-written review at every step.

13. **Parallelize independent investigation; serialize acceptance.** Use non-overlapping ownership or isolated worktrees, private build directories, and a bounded worker pool. Shared compilers, global fingerprints, and metadata may still prevent parallel writes. Retest candidates against the current baseline before serial promotion. Do not assume “research-only” makes shared mutations safe.

14. **Spend stronger reasoning where evidence shows leverage.** Repeated blocker families, contradictory findings, and cross-cutting compiler/linker questions are candidates for synthesis, not automatic Astra assignments. First check whether a Luna worker can investigate them with existing tools and sufficient scope. Count functions actually made eligible by a capability change, including remaining blockers. Group workers by useful evidence or dependencies—not superficial similarity alone.

15. **Measure results without manufacturing credit.** Track integrated exact game bytes/functions, runtime reuse, data ownership, raw debt, and proof scope separately. Record useful negative evidence without counting it as recovered code. Include worker, supervisor, onboarding, handoff, retries, and review in model-weighted cost. Count cached input and reasoning subsets only once.

16. **Validate conclusions as well as code.** Proposal-only tests do not measure recovery throughput; four cases do not establish a universal workflow. Use real diverse tasks, controls, frozen starting evidence, and replications where consequential. Treat learned compiler patterns as scoped observations. Keep current status compact and fingerprinted, archive history, and continue recovery rather than endlessly redesigning its workflow.
