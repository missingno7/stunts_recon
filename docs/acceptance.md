# Acceptance scope

The byte oracle is reconstructed from the four supplied assets using DSI, DIF and EXEPACK decoding. `layout/oracle.lock.json` fixes asset identities, header metadata, complete unpacked image, and the ordered MZ relocation table. The independently unpacked comparison is preserved in `evidence/unpack.json`. Verification never updates expected bytes.

The manifest partitions every initialized load-image byte into matching C CODE/data, matching ASM CODE/data, pinned runtime, or explicit raw ownership. A C CODE owner lists its complete `data_intervals`; each initialized interval also has one `MATCHING_C_DATA` partition owner tied to that CODE owner. `_BSS` contributions use a separate `bss_owners` partition of the verified startup clear range and contribute zero bytes, including any overlap with file-end zero fill. New C recipes must consume every nonempty SEGDEF as a full CODE or reviewed DGROUP contribution. Empty declarations, full public/external lists, all OMF fixups, and exact ordered relocations are checked. No secondary interval may overlap an unrelated accepted owner. An accepted data interval can be subsumed by a larger exact contribution only when its complete extent and bytes remain exact and the recipe names it in `subsumed_data_owners`. Unknown OMF records, corrupt checksums, holes, overflow, and unsupported communal/BIG/32-bit storage fail closed. COMDEF communal allocation order is never inferred: a COMDEF is accepted only as part of the whole LINK c_common unit placed by a real link (integ39 section); any other COMDEF is refused. BSS storage ownership is placed only by a real LINK run (integ32 section). MSC B4/B6 local externals/publics are parsed with their scope intact: each local external resolves to a distinct public inside the object, cannot shadow a global binding, and each local CODE public must be a complete reviewed member of a group recipe. Diagnostic object inspection cannot grant acceptance.

The tested binders support no-fixup contributions, reviewed external DGROUP offsets, external far CALLs, the bounded mixed far-CALL/DGROUP mode, far code-pointer MOV offset/base pairs, paired CS-data offset/base MOVs with far CALLs, and the specific frame-callback object mode. MASM F0 offsets framed by DSEG require exact DGROUP membership and a grounded segment base: either a complete nonempty module DSEG placed by original group-framed CODE references and exact payload, or a zero-length module DSEG tied to the pinned reference first declaration at the independently verified DGROUP base. Bounded displacements must stay inside reviewed data objects. Self-relative external near CALL/JMP fixups require a unique inventory-verified entry or a pinned reference label at a verified original instruction boundary in the caller physical segment, an exact signed displacement, and no MZ relocation. Same-module near JMPs to interior labels require a pinned reference label at an original instruction boundary. The independent DOSBox-X path uses these same binding functions. Secondary DGROUP binding requires exact complete segment length and bound bytes, a raw or exactly subsumed owner, and at least one original CODE fixup whose target segment, group frame, bounded addend, and pristine operand independently place that whole contribution. Every data fixup is bound through reviewed code/data symbols or another complete secondary segment; unsupported shapes fail closed. Data-segment relocations are checked against the original ordered MZ table within their complete intervals. DOSBox-X independently recompiles or reassembles and binds each secondary contribution. The symbol tables check original instruction bytes and relocation anchors. The function inventory supplies address and boundary provenance; source names are binding aliases, not claims about original PUBDEF names or original translation units.

A reviewed far-code alias requires an original `9A` far CALL or an original `MOV AX,offset; MOV DX,segment` pointer pair wholly inside an instruction-verified inventory caller. The segment word needs an MZ relocation, and the offset plus paragraph must land exactly at the independently mapped entry. Complete mapped targets require verified boundaries or emission bytes with start/end evidence, an unchanged original extent, and a complete raw, exact C, exact ASM, or pinned runtime owner. `sprite_make_wnd` now has a separately reviewed complete code-prefix extent through its terminal nonreturn call; the following raw/data region and separately called helper retain separate ownership. For runtime ownership, the pinned OMF public must land exactly at the verified entry and the complete source member must bind. An anchor may lie inside the contribution being proposed because its bytes come from the immutable oracle, independently of candidate output. Every listed anchor is checked anew. Alias spelling must match the inventory name with the C underscore convention or be individually reviewed; it does not assert an original PUBDEF.

The mixed binder accepts one or more external far CALL fixups together with reviewed DGROUP offset fixups in a complete object. It binds every CALL from its reviewed code frame, every data offset from its reviewed DGROUP frame, checks each emitted fixup's shape and location, and preserves the source's exact ordered MZ relocation obligations. Additional CALLs do not relax the complete declaration, public, byte, or whole-image gates.

A DGROUP symbol's fixup addend must remain inside its independently grounded object extent. Reviewed field anchors may authorize their exact element offsets; a symbol without a grounded extent or field permits only addend zero. The resolver supplies these allowed addends to both the data-only and mixed binders. The sole reviewed folded-index exception is `_audiochunks_unk2` at DGROUP `0x86BC`: eight 76-byte records, bounded by original signed guards to indices 16..23. MSC folds `array[i-16]` into a signed `-1216` static addend (`-1214` for its second word). The pinned reference span, two hash-verified callers, exact guard, multiply, and indexed-access instructions, and the next object at `0x891C` are rechecked from the oracle. A recipe using such an addend must list each `folded_index_bindings` offset, field offset, and witness; the original instruction at that fixup site must be the reviewed guarded access. The complete object, fixups, relocations, and whole-image equality remain mandatory. In particular, an expression that reaches a separately labelled global through a large index into another symbol is rejected even if the resulting physical address happens to match the original bytes.

The CS-data mode is limited to the 60-byte `sprite1`/`sprite2` island in seg012. The pinned reference's 60 byte declarations, pristine island hash, a relocated original CS segment word, and separate original offset instructions ground its two 30-byte symbols. Each candidate reference must be a zero-addend adjacent MOV AX offset / MOV DX segment pair; both OMF fixups and the base-word MZ relocation are mandatory. Calls in the same object remain separately grounded far-code aliases. This mode does not grant access to neighbouring code or data.

Compact DGROUP entries record a binding name, original load address, and storage class. At resolution time, the resolver checks the locked image and DGROUP frame, then decodes an unrelocated 16-bit memory displacement equal to that address inside a hash-verified, instruction-verified procedure. Reviewed aliases may instead carry an exact original offset-immediate or displacement instruction plus separately pinned declaration and assembly use lines for that same label. The declaration's cumulative position in the pinned `dseg.asm` must equal the alias's DGROUP offset. An alias naming a pinned reference segment and procedure must have its use line inside that procedure's `PROC`/`ENDP` span, and each anchor must decode as one original instruction, with the 16-bit operand at its recorded offset, inside the same hash-checked, instruction-verified inventory procedure. A displacement plus an unrelated immediate is not an address anchor. Names remain aliases: a reference-source label or candidate spelling does not prove the original C declaration, PUBDEF, or TU. Reviewed widths cite a specific span from one label to the next in the pinned reference `dseg.asm`; that span is a reference hypothesis, not an original-object fact. The spanned label must be placed, by cumulative pinned declaration size, at the alias's own DGROUP offset: a span measured at a label placed elsewhere is rejected rather than granting addends into unrelated objects. Because placement ties the span to the address, an alias spelled differently from the label (for example an address-derived `_word_XXXXX` name) may use the span placed at its address. The `_state` aggregate has a separately reviewed 1,120-byte label span at DGROUP `0x8D24`, ending at the next label `0x9184`; resolution checks the pinned reference identity, recounts the span, calibrates its coordinates against `_gameconfig`, and rejects overlap with another reviewed-width object. Exact reviewed field anchors can separately authorize a field offset. Access width alone never grants an object extent.

The 256 indexed `_g_ascii_props` bytes have a separate pinned declaration and oracle-byte proof; the following byte is checked as padding and grants no index 256. `_audiodriverstring` is a five-byte reference span. `smouspriteptr`, `mmouspriteptr`, and `mouseunkspriteptr` are each one four-byte `dd` declaration in the pinned reference, so their second words are bounded fields of the same pointer instead of separate global allocations.

The reviewed function overlay now checks the complete original table words and bounded destinations for the listed generic switch bodies, including the four draw-line selector tables whose zero/one prefix words are retained but excluded by the reviewed selector domain. Two exact unreachable post-table jumps in `track_setup` and `loop_game` are checked as code bytes and in-function branches, not discarded as padding. The conditional boundary rows with unresolved non-NOP ownership or missing entry anchors remain outside the overlay.

`tools/data_extent_generator.py` scans the locked image and instruction-verified function inventory for a constant scale of an index loaded from the same memory location tested by two dominating bounds. Both bad branches must bypass the indexed access. It normalizes field displacements within a stride, unions bounded witnesses, and rejects storage-boundary crossings, incompatible scales, interior independently anchored symbols, and unbounded indexed displacements within the proposed span. A compact `generated_extent` records the source base, stride, inclusive index bound, field offsets, and access sites; the resolver reruns the scan against the oracle before granting addends. The generated scan also accepts a corroborated ring-buffer extent when an original stride multiplied by a same-index wrap constant equals the exact pinned reference label span, every original write to the index is a constant initialization or guarded wrap, and no other symbol overlaps. For `audio_carstate`, 34 x 40 equals the 1,360-byte `_unk_44F4C` span at DS:`0x97DC`; the complete original index reference/write set, zero initialization, post-access wrap, pinned reference identity, and overlap check are revalidated at binding. The post-access check alone grants no width.

A multi-function recipe names a group and lists every contiguous inventory member with its exact original extent, hash, and emitted public offset. This includes every MSC local CODE public, whose independently reviewed extent is recorded as a local member. One complete object replaces exactly that interval; internal self-relative near CALL fixups use the emitted target public and computed signed displacement, while external fixups use the existing strict binders. A group may subsume an accepted single-function owner only when the recipe lists that owner, its extent equals a group member, and its active source is freshly recompiled to the original bytes. Otherwise the group may replace only raw ownership. Full object declarations, ordered fixups and relocations, and fresh whole-image equality remain required.

A member observed inside a near-call closure can also be a standalone C contribution when its separately compiled complete object has no outgoing near-call dependency and passes the same strict single-function gates. A separately compiled member can still fail when its own OMF FIXUPP order cannot reproduce the original ordered relocation sequence. This ownership can later be subsumed by an exact group recipe. TU-owned `_DATA`, `CONST`, or `_BSS` stays with the source contribution that emits and owns it. The diagnostic TU workbench derives a candidate initialized-data base only when original CODE operands independently agree and the complete emitted segment bytes match that grounded image span; its report does not grant ownership.


An ASM recipe has `kind: asm`, the `masm510-game` profile (`toolchain/msc510-msdos/MASM.EXE`), explicit `assembler_flags: ["/Mx", "/I."]`, a tracked `asm/*.ASM` source, and an empty include closure. `INCLUDE`, `INCBIN`, and `ORG` are excluded from this self-contained profile. The pinned assembler reproduces bytes; it does not identify the historical assembler. The complete emitted OMF SEGDEF/GRPDEF/PUBDEF/EXTDEF declarations and ordered FIXUPPs must equal the recipe, including no-fixup objects. The existing binder and fresh whole-image gate apply to ASM, with bounded MASM source-segment-frame far CALLs, original-frame corroboration, and the reviewed CS sprite-table LEA offset mode. MASM same-segment near CALL FIXUPPs in a multi-routine module bind only to listed member publics. An ASM owner is `MATCHING_ASM`, its secondary data is `MATCHING_ASM_DATA`, and validation counts its bytes separately from C and pinned runtime. DOSBox-X independently reassembles every active ASM source and checks the same complete binding and relocation obligations.

A complete single C module may bind MSC same-segment `offset16` code-table words (switch tables) to its own segment: MSC stores the in-segment offset in the LEDATA word with a zero FIXUPP displacement, the frame is the module's own segment (F0) or target (F5), the offset must lie inside the module, and the recipe's original frame must place the whole module in one 64 KiB frame. Group recipes and self-relative forms remain excluded from this C rule.

MASM DGROUP `offset16` references may use F1 group or F2 external frames when the exact GRPDEF index names DGROUP, or the frame EXTDEF independently resolves inside the same checked DGROUP paragraph. The target still needs a reviewed data alias and bounded addend. Same-segment `_TEXT` `offset16` table entries bind only within the complete single or grouped ASM module; each target displacement must remain inside its owned code extent. A module's own `_TEXT` `base16` MOV DX immediate may coexist with external far CALLs when its original segment paragraph is checked against function evidence and every segment-word MZ relocation appears in the exact oracle order. The pinned DOSBox-X reassembly invokes these same binders. `preRender_helper2` has an additional narrow boundary proof: its pinned Restunts `PROC`/`ENDP` source span, adjacent mapped procedure boundaries, 247-byte oracle hash, and seg012 frame must all agree before promotion.

The reviewed `_main` alias ties CRT0's original relocated far CALL at load offset 118009 to the game's reviewed `ported_stuntsmain_` entry at load offset zero. The pinned CRT0 OMF EXTDEF/FIXUPP site is separately checked when that startup member is staged. The group runtime binder keeps that entry's own paragraph-zero frame. This entry proof does not place CRT0DAT's zero-length linker sections and does not grant startup ownership by itself.

Startup members use four further group-runtime forms, each reviewed per fixup and never derived from the member under test. An external 16-bit code offset (F0 `_TEXT` frame) must be listed in `external_code_offsets`, name a staged pinned `_TEXT` public, and sit in a `MOV r16,imm16`, a `MOV [disp16],imm16`, or a DGROUP word that is exactly a public of the same object. The LINK `/DOSSEG` symbols follow the pinned CRT0 declarations: `_end` is the start of class STACK, placed by the MZ header SS reservation, and `_edata` is the start of class BSS, placed after the accepted `dos\nmsghdr.asm` EPAD section, the last non-BSS section in its pinned SEGDEF order, rounded to the word alignment of `_BSS` over a zero, relocation-free gap. Each reviewed signed addend is listed. CRT0DAT's COMMON `CDATA` and its zero-length DATA-class sections (XIFB..XCFE) are placed backwards from the accepted `HDR` section start (the next DGROUP class) in CRT0DAT's pinned SEGDEF order, across exactly the listed pinned intervening contributions. Each intervening contribution must be a complete word-aligned far-pointer table from a hash-pinned library member. The only current one is `_cflush.asm` XP, 4 bytes. Each pointer must land on its verified inventory entry through an original relocated segment word, and the ordered MZ table must hold no other relocation in the placed span. The neighbour must be another owner already in the canonical manifest. The BSS-class XOB/XO/XOE sections have no independently grounded neighbour: the only operands naming DGROUP 0x72B4 are CRT0DAT's own, the end of the complete `_BSS` is raw, and LINK communal allocation is unsupported. They therefore fail closed, and CRT0DAT, and with it the startup SCC, remains raw.

A group runtime member may bind an exact far CALL (`pointer32`, zero addend) into raw runtime code through a reviewed far code alias listed in `code_aliases`. The alias must resolve through `layout/code-symbols.json` with its own original relocated CALL anchors and verified mapped entry in the runtime `_TEXT` frame. Runtime members are matched by pinned archive/member identities and complete extents. Untouched historical LINK fixtures test ordered LEDATA policies with both pinned compiler distributions. No global checksum or overlap exception exists.

Literal C includes are resolved before compilation: angle headers come only from the hash-pinned profile INCLUDE directory, and quoted headers come only from tracked `include/` files. Search records each included path and SHA-256 in its frozen environment; recipes freeze the same closure, and strict acceptance and DOSBox-X independently verify it. The historical `#pragma pack(1)`, `pack(2)`, `pack(4)`, and `pack()` forms pass through unchanged and are recorded with their source location and value in that closure. The pinned MSC 5.10 `#pragma intrinsic(...)` and `#pragma function(...)` forms are allowed for the MSC 5.10 intrinsic set: the manual's `memcpy`, `memset`, `memcmp`, `strlen`, `strcpy`, `strcat`, `strcmp`, `strset`, `abs`, `labs`, `_rotl`, `_rotr`, `_lrotl`, `_lrotr`, `inp` and `outp`, plus the pinned `README.DOC` additions `inpw`, `outpw`, `_enable`, `_disable` and the floating-point names; each non-floating-point name is tested inline with the pinned compiler. Their ordered names and source locations are frozen in the same closure. Other pragmas and names are rejected. Sources without includes or supported pragmas have an empty closure.

The compiler profile is a compatibility hypothesis: Microsoft C 5.10 medium model with `/O /Gs` is pinned, but matching code under 5.00 prevents a unique historical version claim. Original TU grouping, general linking, arbitrary segment/frame modes, QuickC BAKPAT, local communal records, and unreviewed CS-relative storage remain technical work. Search can inspect unsupported objects and context hypotheses without weakening production.

Complete ASM modules may bind direct CS memory operands only to the reviewed sprite or interpolation data extents, with a CS override, a complete displacement field, and an in-object addend. A local far CALL or JMP may target an interior label only in one complete module with its original CODE frame and exact MZ segment-word relocation. Multi-function promotion may subsume a previously accepted group only when every ordered member identity is retained in one contiguous slice and that entire accepted group freshly verifies. Ordered MZ relocation sites must follow the candidate object's own FIXUPP and CODE record structure. The CODE cut simulator applies the validated MSC 5.10 record rule. A CODE LEDATA record closes after the emission unit that brings it to at least 944 bytes, or after the unit carrying its 99th FIXUPP; observed records hold at most 949 bytes. A `jcc $+3` followed by a near JMP is one unit, and each switch-table word is one unit. Regression tests compile accepted recipes and bounded probes with the pinned compiler, then compare the rule against their observed OMF records. Observed LEDATA ends remain the exact diagnostic, and the simulator reports every record that disagrees with the rule. It is diagnostic only and never supplies relocation order.

`--verify-only` for C, ASM and runtime candidates does not take the exclusive writer lock. It reads canonical inputs under a publication sequence number that each publisher makes odd before journaling or writing and even only after its journal is gone; a check that starts during a publication, or observes a changed sequence number, journal, or canonical input identity, reports a retryable snapshot change and never a verification result. Publication itself keeps the exclusive lock, journal, and rollback. Promotion preserves all existing owner intervals except the explicitly listed, freshly reverified owners subsumed by a multi-function contribution. A new single function or complete pinned runtime member can replace only a wholly raw interval. Runtime publication uses `promote_runtime.py` and the same exclusive lock, staged whole-image build, journal, input snapshot, canonical whole-image build, and rollback path as C promotion. Replacing an accepted function requires the same interval and fresh exact output. Canonical input identities are checked before and throughout serialized publication. Scratch histories are outside acceptance inputs.

Full validation combines negative technical tests, fresh pinned C compilation, runtime binding, complete hybrid image and ordered relocation equality, and independent DOSBox-X recompilation. Reports are derived under `build/validation/` and `build/exact/`. Source hashes, object bytes, and every binding are checked anew; historical receipts cannot authorize acceptance.
# Data-only modules

A `data_only` recipe identifies a complete C or ASM OMF module with zero CODE length, full segment declarations, publics, externals, LEDATA, and ordered FIXUPPs. Its complete initialized `_DATA` extent is a standalone `MATCHING_C_DATA` or `MATCHING_ASM_DATA` owner. C is the default classification because the image does not distinguish C from MASM data; ASM requires positive evidence. The hybrid placement gate uses unrelocated original CODE operand words, including raw CODE, to ground one module base and checks every recorded public/alias offset against it. Native LINK slot uniqueness and a full normal LINK image remain final closure work.

Every offset16 pointer FIXUPP is bound to a complete in-module public object or independently grounded external DGROUP object, with its addend inside that object and its two bound bytes exact in the oracle. The binder rejects other emitted nonempty segments, unexpected fixups, extra bytes, moved publics, and module boundaries that break MSC word alignment. A larger exact module may subsume complete accepted data owners through an explicit `subsumed_data_owners` list; previously accepted code and all other owners remain independently recompiled. The whole staged image and ordered MZ relocations must still match. The independent DOSBox-X crosscheck recompiles every active standalone data module.
# Per-object flags, whole ASM modules and far data (integ24)

The canonical C profile stays `/AM /O /Gs`. A C recipe may carry a reviewed `compiler_flags` set, with its `compiler_flags_register` id, only when every function it contributes belongs to one object named by a SUPPORTED `TUFLAG-*` register entry and the flags equal that entry's ruled set (`tools/object_flags.py`: `/AM /Oa /Gs` for seg014, seg015, seg019 and seg021-seg025; `/AM /Ox /Gs` for seg027 and seg030). The register is re-read on every use; a status, scope or ruling change refuses the override. The set applies to the whole object: every canonical-flag C contribution inside a flagged object must emit the identical complete object under the object's set as well, on every build and in the DOSBox-X crosscheck. Flag sets are reproduction profiles, not provenance claims.

A whole-module ASM recipe (`module_proof`, kind `asm-module-extent-v1`) covers one complete assembled module as one contribution. Both ends are rechecked from the oracle: a zero fill byte after an unconditional transfer (outside the module, or as the module's own terminal byte when an accepted owner already holds it), or a verified neighbouring function in another code frame. Every public entry lands on an inventory-verified start in the module frame; an entry whose inventory row is only partially mapped needs original relocated far CALLs from instruction-verified callers outside the module. A labelled data table inside a verified module procedure may be a declared embedded public. Procedure ends and internal labels are not required individually; a verified procedure may not cross either module end, and an inventory row may run past the end only by the one clipped fill byte. Declarations, ordered FIXUPPs, bytes, ordered MZ relocations and fresh whole-image equality remain mandatory. A module may subsume accepted ASM owners that start at its entries and end at an entry, a verified function end or the module end, each freshly reproduced.

Only such a grounded module may subsume an accepted C owner inside it. The C owner is reclassified MATCHING_ASM and its source retired from ownership (recorded as `reclassified_owners`) when a same-module link is rechecked: an odd start without a pad byte (MSC word-aligns every function), an original rel8 branch crossing the owner boundary, or membership of the module's shared ASM code frame strictly inside a zero-fill-bounded module with no fill at either owner edge. Ordinary groups still cannot cross kinds.

MASM 5.10 keeps 31 significant characters of a name. An ASM member or module public may be the truncated spelling of its longer inventory name; far-code and data aliases accept a truncated spelling only when marked `masm_truncated_public`, and still resolve the full inventory entry or pinned label.

A far-data module (`data_only` plus `far_data`) is one complete paragraph-aligned FAR_DATA segment with no FIXUPPs and publics whose declared sizes cover it. Its placement needs at least one original relocated segment word whose paragraph equals the module start: an immediate in an instruction-verified procedure, or a DGROUP word declared `dw seg X` at its placed pinned label. Optional offset anchors tie public offsets. C is the default classification.

Per-fixup composition also covers reviewed CS-island data: an adjacent MOV AX offset / MOV DX segment pair beside far CALLs and DGROUP offsets, and CS-override memory operands in composed ASM modules. The reviewed CS operand forms add `MOV Sreg,mem`, `ADD r16,mem` and `IDIV mem`. Generic CS islands (for example the 256-byte `incnums` table) are rechecked from their pinned `db` listing, label placement, width and one original unrelocated operand in a verified procedure of the same frame. External far JMP thunks (`EA`) bind like far CALLs, and a relocated far JMP anchor grounds a code alias like a far CALL. An emission-verified entry bounded on both sides by instruction-verified neighbours may ground a code alias or a single ASM recipe when marked `verified-neighbours-v1`.

A 4-byte `dd` object whose pinned single-declaration span is placed at the alias address, and which original code accesses as a far pointer (LES/LDS or its +2 word), has width 4, so segment-half addends are in-object. A placement-checked label with a reviewed width may be anchored by an original access to an element inside its extent (`field_offset`). Data aliases whose spelling named a label placed elsewhere in the pinned reference were corrected: the address keeps the label actually placed there (or its existing address alias), and the old spelling is re-derived at its own placed label with an original anchor; each change is listed in `renamed_aliases`.

Pinned toolchain files keep their logical `toolchain/...` identities; a profile's `directory` may name a hash-identical copy elsewhere (`logical_directory` maps the logical paths). The independent crosscheck runs the hash-identical DOSBox-X copy at `C:/tools/dosbox-x/dosbox-x.exe`.

# Record-closed prefix proof (integP)

Intermediate ownership may cover the leading part of one original object before the whole object matches. It is monotonic and disposable: a longer prefix or the complete object replaces it, and final closure never depends on it.

**Source of truth.** The proof compiles the complete candidate translation unit with the pinned compiler (and the object's registered flag set, if any) as one object. That object's CODE offset zero, its first public, is placed at the object start. The object start must be a verified inventory entry of that public. It must also be the start of its code frame. The frame comes from the inventory paragraph, or from the entry's reviewed far-code alias with rechecked original relocated anchors. The start must lie in the frame's first paragraph, and no inventory row may start between the frame base and it. Record boundaries are the candidate's own CODE LEDATA records, read from its emitted OMF (`cut_simulator.ordered_data_records`). Each FIXUPP belongs to the record it follows. The candidate relocation stream is those FIXUPPs in emitted order: records ascending, FIXUPP order within a record, `pointer32` and `base16` generating MZ entries. It is never sorted, rewritten, simulated, or taken from oracle record boundaries or oracle order. The Restunts TU grouping is not assumed. The oracle is used only afterwards, for comparison.

**States.** `CODEGEN_EXACT`: a record's bytes outside FIXUPP fields and its relocation-site set agree with the oracle; binding or order is unproven. `EXACT_OPEN_RECORD`: bound bytes, fixups and order are exact, but the record is the final candidate record, which the compiler closed only because the candidate ended. Its cut, and therefore its relocation order, is not proven. `RECORD_CLOSED_EXACT`: the record is inside the derived prefix. `ACCEPTED`: the interval is owned by the manifest. Reports also use `BOUND_EXACT_AFTER_GAP` for an exact closed record after an earlier failing record, and `MISMATCH`.

**Rule.** The derived prefix is the longest run of records 0..k that meets four conditions. (i) Each record is naturally closed: a later CODE record of the same object follows it, so the final record never counts. (ii) Each record is byte-identical to the oracle at object start plus offset. (iii) Every FIXUPP in the run is bound by the existing binder rules with exact bound bytes. (iv) The run's candidate-derived relocation stream equals the oracle's relocation subsequence for the same interval, in order. Condition (iv) is checked per record and again cumulatively. Existing binder rules cover: external binders by shape-selected existing mode through `bind_contribution`; same-object near CALLs to publics; C switch-table `offset16` words under the single-C-module rule; and TU-owned `_DATA`/`CONST`/`_BSS` through `bind_secondary`. TU-owned data is placed only where original CODE operands agree on one base, as tubench does. The complete emitted segment must be exact, so only proven data bytes are owned. Every candidate public inside the prefix must be its verified inventory entry, and inventory rows must tile the candidate publics. A near-CALL target must be the verified entry of its public. A prefix may end in the middle of a function; the recipe records `ends_mid_function`. Everything after the prefix is at most `CODEGEN_EXACT`/`EXACT_OPEN_RECORD` and stays raw.

**Suffix dependencies.** Bytes in closed records can depend on later code. Examples are forward jump displacements, near CALLs to later publics, switch-table targets and jump sizes. That is acceptable only because those bytes are compared with the oracle, and because the proof is re-derived from a fresh compile of the full canonical candidate on every probe, validation and DOSBox-X crosscheck. No proof is stored or cached. The proof lists these dependencies (`suffix_dependencies`). Suffix code that no closed-record byte depends on leaves the prefix unchanged (`test_suffix_change_without_dependency_keeps_prefix`). A suffix change that moves a target a closed record references invalidates or moves the prefix. That is correct fail-closed behaviour (`test_suffix_change_with_forward_dependency_invalidates_prefix`). The open record is never owned. Closing it by adding code extends the prefix only if the newly closed record is exact. A changed FIXUPP inside it stops the extension. An added FIXUPP before a natural close changes the candidate stream and cut, and the proof follows the candidate.

**Ownership.** A prefix recipe has `prefix_of_object` (schema `record-closed-prefix-v1`, object start, record count, record ends, candidate object length, `ends_mid_function`) and `prefix_members` (inventory rows, complete or partial). It also carries the full candidate source, the complete object declarations, the owned records' ordered FIXUPPs and the oracle relocation obligations. A fixed key set excludes any diagnostic field and `relocation_order_basis`. The manifest row is `MATCHING_C` with `contribution_form: prefix_of_object`, `object_start` and `prefix_records`. `probe`, `build_exact` and `crosscheck_runner` re-derive the proof with `prefix_proof.bind_prefix`. They fail, never shrink silently, when the re-derived prefix is shorter than the owned interval or no longer ends at the owned record boundary. A prefix may subsume accepted owners wholly inside it at exact complete member extents, or a shorter prefix of the same object start. It cannot cut an accepted owner. Only a longer prefix, or a complete object from the same start, subsumes a prefix owner, using the existing subsumption path. The complete contribution is verified on its own, and `replace_group` never consults the prefix proof for it.

**Tools and reports.** Use `python tools/prefix_proof.py SOURCE --report OUT.json [--recipe-out R.json --id ID]` for research. Its report holds per-record states and failure categories (`OBJECT_START`, `OPEN_RECORD`, `PUBLIC_ENTRY`, `SYMBOL_BINDING`, `FIXUP_BINDING`, `TU_DATA`, `BYTE_MISMATCH`, `RELOCATION_ORDER`, `UNSUPPORTED_RELOCATION`), member states, suffix dependencies, and a classifier view (`prefix_proof.prove_source`, `classifier_view`). `promote.py --verify-only` prints owned and re-derived records with the record states. `validate.py` reports `record_closed_prefixes` from the fresh build. Cut-simulator, blockdiff, classifier and tubench results never enter a prefix proof, and no report under `build/` confers ownership.

A reviewed far-code alias may name the verified entry of any listed prefix member, including the member cut at the prefix end. The remainder of that member stays raw. Separately, a complete C module bound through the composed switch-table path compares its ordered FIXUPP-derived relocation stream, as the other C binders do. The former MASM site-multiset rule was removed by integ25 (next section).

# Candidate-ordered relocations, object forms and aliases (integ25)

**Relocation order.** Every binder, C or ASM, single or group, derives the object's MZ entries from its own FIXUPPs in emitted order (`pointer32` at +2, `base16` at +0) and compares that stream, in order, with the recipe obligations and the oracle; it is never sorted into, or taken from, the oracle order. The model is the pinned LINK's behaviour: `tools/link_order_probe.py` links a MASM 5.10 module with ascending FIXUPPs over several LEDATA records and an MSC object with descending FIXUPPs, unchanged, with both pinned LINK versions (3.65, 3.61); each keeps FIXUPP order. The only transformation is EXEPACK's stable regrouping into 64 KiB banks. Group recipes compare the complete candidate stream (external calls, same-module far transfers and segment words together). Re-verifying every accepted MATCHING_ASM owner under this rule failed `frame_callback_replay_group` (16 relocations) and `obj_seg007_complete` (44): their MASM FIXUPPs ascend while the oracle holds descending runs per record, which the pinned assembler cannot emit. Both were demoted to UNRESOLVED_RAW (sources kept under `build/workers/integ25/demoted/`). No accepted MATCHING_ASM owner relied on `F3 A6` as its only positive ASM marker.

**Hard-coded program addresses.** Before binding, every original MZ-relocated word wholly inside the contribution (CODE and owned secondary segments) must be generated by a candidate FIXUPP at that site. A literal segment:offset standing in for a relocation (for example a far pointer constant) is rejected as a hard-coded program address, in the probe and in the DOSBox-X crosscheck.

**Per-object flags.** `tools/object_flags.py` adds seg032 to the `/Oa` entry, `/AM /Ox /Gs` for seg029 (`TUFLAG-Ox-seg029`) and seg028 (`TUFLAG-Ox-seg028`, member level). For seg028 the DS reload may be spelled with `_loadds` under `/AM /Ox /Gs` or as the flag set `/AM /Au /Ox /Gs`; both emit the identical object (NON_DISCRIMINATING) and the recipe records the set it uses.

**C object forms.** MSC 5.10 emits C publics and externals with 31 identifier characters plus the underscore; a C group member public may be that truncation of its inventory name, and a far-code alias may be when marked `c_truncated_public`. A group recipe may own a reviewed `object_tail` (`msc-code-object-tail-v1`): only `90` pads followed by declared-but-uninitialised zero bytes after an unconditional transfer ending the last member, at most four bytes, overlapping no inventory row, with the matching CODE `sparse_zero` initialised prefix. Secondary `_DATA`/`CONST` may carry an `initialized_ranges` `sparse_zero` policy whose gaps are single bytes before word-aligned offsets (MSC alignment holes). Both are zero in the image and compared like all other bytes. A record-closed prefix may carry the same alignment-hole policy for TU data it does not own, only so that the whole candidate object can be read; research compiles (prefix_proof, tubench) derive that policy only for the MSC alignment-hole shape. Far CALLs plus the pinned absolute `__AHSHIFT` word form a complete mixed object without DGROUP data. A C group with own-segment switch-table words binds them at the members' inventory code frame, which the recipe's `original_frame_load_address` must equal.

**Far data and module entries.** A public of an accepted FAR_DATA module (`far_data` owner) binds as far data: its offset16 inside the declared public object and its `base16` segment word, each the immediate of a MOV, with the paragraph re-grounded from the module's relocated segment-word anchors. A far-code alias may name a PARTIAL_UNMAPPED entry listed by an accepted whole ASM module (`module_entry`), whose module proof re-grounds the entry; the alias's own relocated far CALL anchors are checked as usual. A code segment's frame may be qualified by one original relocated far CALL from an instruction-verified caller onto a mapped entry of that segment (`function_evidence.SEGMENT_FRAME_ANCHORS`, seg037).

**Aliases.** Aliases are binding names only: they do not claim an original PUBDEF, source name or translation unit. `tools/autosym.py` derives far-code (`_code_<stable_id>`) and DGROUP aliases (pinned label spelling) from the oracle, the inventory and the pinned reference listings only, with receipts; inventory C spellings of the same code entries use the same anchors. An existing alias at an interior address of a placed label span is a sub-object or field name for the same address, not a conflict: the container keeps its label-span width and the interior aliases keep their own addresses; only a partially overlapping object refuses a width. Reviewed refusals (`autosym.WIDTH_REFUSED`, e.g. `_byte_428D6`, whose only interior reference is a separate copy destination) are not granted.

**Diagnostics.** `tools/classify.py`, `tools/status_report.py`, `tools/classifier_cases.py`, `tools/blockdiff.py` and `tools/pcore.py` are diagnostic only and never imported by the acceptance path; `--record-proof auto` derives the classifier view with `prefix_proof.prove_source`, and `--symbol-receipts autosym` reads autosym output. Their reports never confer ownership.

# Pass environment, register-gated MSC 6.00A profile and address lint (integ27)

**Pass environment.** MSC CL starts each pass with an environment it builds itself: `MSC_CMD_FLAGS` (with `-il` naming the TEMP prefix and `-ef` naming the pass directory's `c23.err`), `NO87=`, `;C_FILE_INFO` and the pass path. # Batch publication, session reuse, LINK fill, negative folded indices (integ28)

**Batch publication.** `python tools/promote.py --batch FILE` (lines `NAME CANDIDATE [RECIPE]`) publishes several candidates in one journaled transaction under the exclusive writer lock (`tools/batch_publish.py`). Each candidate is first verified individually: a fresh probe of its complete contribution, its ownership change against the canonical manifest (with fresh probes of every owner it subsumes) and an independent DOSBox-X compile or assembly bound by the same binders (`crosscheck_runner.independent_row`). The survivors are composed into one staged manifest and checked by one fresh whole-image build that recompiles every active contribution and compares the ordered relocations. A candidate whose own contribution fails that build (the build attributes the failing owner) is dropped and a new fresh build runs for the rest; a failure that no single owner explains is bisected over the batch order, each step a fresh build. A concurrent change of canonical inputs aborts the batch instead of being charged to a candidate. Sources, recipes and the manifest are then written under one journal, the canonical image is rebuilt freshly, and any failure rolls the whole batch back. `--verify-only` runs every gate without the lock and without writes; `--no-independent` is refused for publication.

**Session reuse.** Within one fresh build, probe, crosscheck or batch stage (`tools/memo.py`), deterministic evidence checks with identical arguments are computed once: the function inventory with its reviewed overlays, the reviewed function evidence, per-name DGROUP symbol resolution, the reference label placement of the pinned `dseg.asm`, and pinned toolchain identities. Nothing is stored on disk or reused by another session; every caller still requires unchanged canonical inputs at its end; toolchain identities are recomputed uncached when the session ends, and after any reuse every pinned reference evidence file is hashed again. The decoded oracle is reused only for byte-identical assets, which are re-read and re-hashed on every call. Probe diagnostics (similarity reports) are computed only for failures. Compilation, binding and all acceptance comparisons are never reused. The build compiles contributions concurrently (`STUNTS_BUILD_WORKERS`) and reports failures in manifest order.

**LINK fill.** Zero bytes between an object's last byte and the paragraph-aligned start of the next segment are LINK alignment fill owned by no object (`LINK_FILL`, `tools/link_fill.py`). A fill owner is re-derived on every build: 1..15 zero bytes ending exactly at the next paragraph boundary, preceded by a complete accepted object contribution (not a prefix) that the row names, and followed by a segment that starts there and requires paragraph alignment: an accepted contribution whose own emitted SEGDEF has paragraph or page alignment, or an instruction-verified code entry whose grounded segment paragraph starts there. A recipe claims it with `link_fill: {end, basis: link-paragraph-alignment-v1}`; it confers no source, code or data ownership and is counted separately (`link_fill_bytes`). seg037 `file_load_shape2d_expandedsize` is a 138-byte C contribution (reviewed instruction-verified extent ending at its RETF) followed by 12 fill bytes before the paragraph-aligned FAR_DATA module at 0x2B1C0.

**Negative folded index.** MSC folds `a[i - k]` into the EXTDEF of `a` with displacement `-k*sizeof(element)`. Such an addend binds only when the recipe lists the FIXUPP in `negative_folded_index_bindings` (form `negative folded index a[i-k]`) and `data_symbols.check_negative_folds` confirms from the oracle that (1) the original instruction at the FIXUPP site is runtime-indexed (BX/SI/DI base or SI/DI index), (2) its displacement is the grounded symbol minus k (1..2) elements of the recorded element size, which divides the symbol's grounded extent, (3) the same instruction-verified procedure accesses the same array at a non-negative element offset (the recorded witness), with both indices loaded from the same recorded operand shortly before, and (4) no unlisted FIXUPP uses that addend. Whole seg004 binds `trackrows[row - 1]` (`_trackrows-2`, witness `trackrows[row]`, index `[bp+8]`) this way. seg030 `audio_filetemp[len - 4]` stays refused: k = 4 and the only other access is a direct store without an index.

**Composed `__AHSHIFT`.** The composed binder accepts the pinned absolute `__AHSHIFT` word exactly as the mixed binder does: a zero-addend `MOV CX,imm16` receiving 12, with no MZ relocation (whole seg005).

**ASM data bytes.** obj_seg002 no longer spells `push ds; lds dx,[06BCh]; mov ah,25h; mov al,0; int 21h` as `db` bytes; the mnemonics assemble to the same bytes with a symbolic `_old_intr0_handler` FIXUPP.

**Names.** `tools/namefit.py` (check, window, refs, apply, solve with `tools/nfsolve.py` and `tools/natnames.py`) and `tools/typeinfer.py` (with `tools/cdecls.py`) are diagnostic tools; their caches and reports live under `build/namefit/`. The seg003 whole object uses the integ28 names registry proposal (`build/namefit/names_registry_integ28.json`): typenames plan C re-solved with a lower naturalness bound, seg003-defined functions keeping their inventory names, and hand-chosen readable spellings, verified by compiling every accepted TU. Its global names are address-bound binding aliases (`clone_of` data aliases, `reviewed_alias` far-code aliases) with `name_provenance: pressure-constrained reconstruction name`. `_unk_3C0EE` keeps no container width: skybox_op reads `word_2C0FC[i]` for i = 2..5, that is DS:990h..997h, outside [97Eh,990h); the fence lists are referenced through their own pinned labels.

# Link fidelity and the real-link diagnostic (integ29)

**Real link (diagnostic).** `tools/reallink.py` (and `python tools/validate.py --image`, which writes `build/validation/real-link.json`) rebuilds the executable with one run of the pinned LINK 3.65 (`/DOSSEG /NOI /NOD /MAP /CP:1`) and the pinned EXEPACK from freshly compiled accepted objects, pinned runtime members, explicit raw-debt objects (original bytes plus one FIXUPP per original relocation) and alias PUBDEF shims. Its unit map is `layout/link-objects.json`. It grants and gates nothing. Its default processing order is **oracle-derived** (address order, segment first appearance, DGROUP order and the oracle's per-bank relocation order) and is reported as such (`order_basis`); `--order library` instead links seg000-seg009 explicitly and lets LINK load the runtime (`RT.LIB`) and game (`GAME.LIB`) modules itself. A single zero byte at an odd address directly before an accepted word-aligned `_DATA` contribution is LINK alignment fill, and the zero byte at 199993 before the WORD-aligned `_BSS` is not written by LINK. After the integ29 corrections the oracle-order link reproduces the load image, all 2,588 relocations in EXEPACK bank order, the header and the packed file byte for byte; raw debt, alias shims and the oracle-derived order remain explicit.

**Ownership corrections.** An accepted owner whose extent or kind contradicts a link fact is corrected by one batch transaction: the recipe carries `ownership_correction` (`ownership-correction-v1`: the owner id, its exact current kind/extent/data intervals, a recorded reason and one basis). The owner and its data rows return to explicit raw ownership, and the corrected contribution is then verified and published by the ordinary strict path; the new row keeps `ownership_corrections` with the reason and previous extent. Bases: `link-data-alignment` (an MSC `_DATA` SEGDEF is WORD aligned and cannot start at an odd address), `link-frame-reassignment` (an original relocated pointer places a routine in another code frame), `odd-start-asm-continuation` (an accepted C owner at an odd address without pad directly after accepted ASM is reclassified MATCHING_ASM over the same extent) and `owner-identity-repair` (an owner row without id is republished with its inventory stable id). Corrections applied: seg003 `_DATA` starts at 180578 (its own literals `crak`, `cinf`, `scensce2sce3sce4`; the former 57-byte struct is the literals of `load_sdgame2_shapes`/`setup_intro` plus the word-aligned `aCarcoun_0`), seg031 `_DATA` starts at 199442 with its own `char audiodriverstring[] = "pc15"`, seg017 ends at 158450 and `nopsub_36AF2` [158450,158452) is a separate two-byte MSC object in the 0x26AF frame (seg008 loads it as the relocated pointer 26AF:0002; the reviewed gap entry records that `frame_anchor`), `mmgr_get_ofs_diff` is ASM, and `set_fontdefseg` has the owner id `asm_load_24b7c`.

**Link-faithful ASM.** Every ASM contribution's code segment is the output segment of its original code frame (`S002_TEXT`, `S012_TEXT`, `S018_TEXT`; class CODE; reconstruction names spelled like C objects compiled as `S0nn.C`), BYTE-aligned when it starts at an odd address. An external far pointer or segment word framed on the module's own code segment (F0: `extrn X:far` declared inside the segment) must name a target in the module's own original frame; otherwise the declaration belongs outside every segment (F2), where LINK frames on the target (`tools/link_frames.py`, checked in every probe and in the DOSBox-X crosscheck; `python tools/link_frames.py` lints sources). Cross-object references of ASM modules use the defining public (`_add_exit_handler`, `_kb_checking`, ...), and the interior label `_loc_3180A` is a declared embedded public of `asm012_137138`.

# Real-link BSS ownership, the link stack recipe and seg012 module data (integ32)

- MASM always writes the length as an `81h` word leaf; MSC writes one byte below 80h.
- MASM writes its COMDEF records in its symbol-table order, not in declaration order. This matters for the within-module first-sight position of ASM-only communals.

**Whole-unit acceptance (`tools/communal_unit.py`).** The communal order depends on every name in the program, so the unit [207408,_end) is accepted in one transaction or stays one raw unit. One `bss_owners` row of kind `LINK_COMMUNAL` (placement `link-communal-v1`, schema `communal-unit-v1`) replaces the raw unit exactly. It lists every communal: name, address, size, declaring owners and a size basis. The addresses must tile the unit by LINK's allocation rule (an even-sized communal starts even). The row is accepted only when all four conditions hold:
- **(a) Declarers.** Each declaring unit is an accepted, exact owner: a C recipe whose `communal_declarations` list its COMDEF records in order (tentative definitions), an ASM module (`COMM NEAR`), or the pinned `_file.c` member. The row's declarers and sizes (the largest declared size) must equal the recipes' declarations. They are re-derived again from the linked objects' COMDEF records, and no object may declare a COMDEF outside the unit. Without an accepted unit, no recipe may declare any COMDEF. `probe_module` and the DOSBox-X crosscheck admit exactly the declared COMDEFs, and `object_probe.declared_externals` excludes an unreferenced tentative definition from the binders' use checks.
- **(b) Placement.** One staged real link reproduces the image (the existing BSS gate) and places every communal:
  - its MAP public;
  - the MAP `c_common` segment;
  - the linked operand of every FIXUPP that names it, in every linked accepted object (`communal_unit.linked_references`, `reallink.communal_placement`).
- **(c) Names.** Each name is the `names-registry.json` name of its address, or the pinned member's own COMDEF name for `pinned-member` rows. Address-derived and solver-placeholder spellings are refused (`is_placeholder`).
- **(d) Sizes grounded.** The size basis is one of four kinds:
  - `declared-type`: the declaration text appears in a declaring source;
  - `pinned-member`;
