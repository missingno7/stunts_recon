# Acceptance scope

The byte oracle is reconstructed from the four supplied assets using DSI, DIF and EXEPACK decoding. `layout/oracle.lock.json` fixes asset identities, header metadata, complete unpacked image, and the ordered MZ relocation table. The independently unpacked comparison is preserved in `evidence/unpack.json`. Verification never updates expected bytes.

The manifest partitions every initialized load-image byte into matching C CODE/data, matching ASM CODE/data, pinned runtime, or explicit raw ownership. A C CODE owner lists its complete `data_intervals`; each initialized interval also has one `MATCHING_C_DATA` partition owner tied to that CODE owner. `_BSS` contributions use a separate `bss_owners` partition of the verified startup clear range and contribute zero bytes, including any overlap with file-end zero fill. New C recipes must consume every nonempty SEGDEF as a full CODE or reviewed DGROUP contribution. Empty declarations, full public/external lists, all OMF fixups, and exact ordered relocations are checked. No secondary interval may overlap an unrelated accepted owner. An accepted data interval can be subsumed by a larger exact contribution only when its complete extent and bytes remain exact and the recipe names it in `subsumed_data_owners`. Unknown OMF records, corrupt checksums, holes, overflow, and unsupported communal/BIG/32-bit storage fail closed. COMDEF communal allocation is explicitly deferred: neither its allocation order nor its storage ownership is inferred, and production rejects it. MSC B4/B6 local externals/publics are parsed with their scope intact: each local external resolves to a distinct public inside the object, cannot shadow a global binding, and each local CODE public must be a complete reviewed member of a group recipe. Diagnostic object inspection cannot grant acceptance.

The tested binders support no-fixup contributions, reviewed external DGROUP offsets, external far CALLs, the bounded mixed far-CALL/DGROUP mode, far code-pointer MOV offset/base pairs, paired CS-data offset/base MOVs with far CALLs, and the specific frame-callback object mode. MASM F0 offsets framed by DSEG require exact DGROUP membership and a grounded segment base: either a complete nonempty module DSEG placed by original group-framed CODE references and exact payload, or a zero-length module DSEG tied to the pinned reference first declaration at the independently verified DGROUP base. Bounded displacements must stay inside reviewed data objects. Self-relative external near CALL/JMP fixups require a unique inventory-verified entry or a pinned reference label at a verified original instruction boundary in the caller physical segment, an exact signed displacement, and no MZ relocation. Same-module near JMPs to interior labels require a pinned reference label at an original instruction boundary. The independent DOSBox-X path uses these same binding functions. Secondary DGROUP binding requires exact complete segment length and bound bytes, a raw or exactly subsumed owner, and at least one original CODE fixup whose target segment, group frame, bounded addend, and pristine operand independently place that whole contribution. Every data fixup is bound through reviewed code/data symbols or another complete secondary segment; unsupported shapes fail closed. Data-segment relocations are checked against the original ordered MZ table within their complete intervals. DOSBox-X independently recompiles or reassembles and binds each secondary contribution. The symbol tables check original instruction bytes and relocation anchors. The function inventory supplies address and boundary provenance; source names are binding aliases, not claims about original PUBDEF names or original translation units.

A reviewed far-code alias requires an original `9A` far CALL or an original `MOV AX,offset; MOV DX,segment` pointer pair wholly inside an instruction-verified inventory caller. The segment word needs an MZ relocation, and the offset plus paragraph must land exactly at the independently mapped entry. Complete mapped targets require verified boundaries or emission bytes with start/end evidence, an unchanged original extent, and a complete raw, exact C, exact ASM, or pinned runtime owner. `sprite_make_wnd` now has a separately reviewed complete code-prefix extent through its terminal nonreturn call; the following raw/data region and separately called helper retain separate ownership. For runtime ownership, the pinned OMF public must land exactly at the verified entry and the complete source member must bind. An anchor may lie inside the contribution being proposed because its bytes come from the immutable oracle, independently of candidate output. Every listed anchor is checked anew. Alias spelling must match the inventory name with the C underscore convention or be individually reviewed; it does not assert an original PUBDEF.

The mixed binder accepts one or more external far CALL fixups together with reviewed DGROUP offset fixups in a complete object. It binds every CALL from its reviewed code frame, every data offset from its reviewed DGROUP frame, checks each emitted fixup's shape and location, and preserves the source's exact ordered MZ relocation obligations. Additional CALLs do not relax the complete declaration, public, byte, or whole-image gates.

A DGROUP symbol's fixup addend must remain inside its independently grounded object extent. Reviewed field anchors may authorize their exact element offsets; a symbol without a grounded extent or field permits only addend zero. The resolver supplies these allowed addends to both the data-only and mixed binders. The sole reviewed folded-index exception is `_audiochunks_unk2` at DGROUP `0x86BC`: eight 76-byte records, bounded by original signed guards to indices 16..23. MSC folds `array[i-16]` into a signed `-1216` static addend (`-1214` for its second word). The pinned reference span, two hash-verified callers, exact guard, multiply, and indexed-access instructions, and the next object at `0x891C` are rechecked from the oracle. A recipe using such an addend must list each `folded_index_bindings` offset, field offset, and witness; the original instruction at that fixup site must be the reviewed guarded access. The complete object, fixups, relocations, and whole-image equality remain mandatory. In particular, an expression that reaches a separately labelled global through a large index into another symbol is rejected even if the resulting physical address happens to match the original bytes.

The CS-data mode is limited to the 60-byte `sprite1`/`sprite2` island in seg012. The pinned reference's 60 byte declarations, pristine island hash, a relocated original CS segment word, and separate original offset instructions ground its two 30-byte symbols. Each candidate reference must be a zero-addend adjacent MOV AX offset / MOV DX segment pair; both OMF fixups and the base-word MZ relocation are mandatory. Calls in the same object remain separately grounded far-code aliases. This mode does not grant access to neighbouring code or data.

Compact DGROUP entries record a binding name, original load address, and storage class. At resolution time, the resolver checks the locked image and DGROUP frame, then decodes an unrelocated 16-bit memory displacement equal to that address inside a hash-verified, instruction-verified procedure. Reviewed aliases may instead carry an exact original offset-immediate or displacement instruction plus separately pinned declaration and assembly use lines for that same label. The declaration's cumulative position in the pinned `dseg.asm` must equal the alias's DGROUP offset. An alias naming a pinned reference segment and procedure must have its use line inside that procedure's `PROC`/`ENDP` span, and each anchor must decode as one original instruction, with the 16-bit operand at its recorded offset, inside the same hash-checked, instruction-verified inventory procedure. A displacement plus an unrelated immediate is not an address anchor. Names remain aliases: a reference-source label or candidate spelling does not prove the original C declaration, PUBDEF, or TU. Reviewed widths cite a specific span from one label to the next in the pinned reference `dseg.asm`; that span is a reference hypothesis, not an original-object fact. The spanned label must be placed, by cumulative pinned declaration size, at the alias's own DGROUP offset: a span measured at a label placed elsewhere is rejected rather than granting addends into unrelated objects. Because placement ties the span to the address, an alias spelled differently from the label (for example an address-derived `_word_XXXXX` name) may use the span placed at its address. The `_state` aggregate has a separately reviewed 1,120-byte label span at DGROUP `0x8D24`, ending at the next label `0x9184`; resolution checks the pinned reference identity, recounts the span, calibrates its coordinates against `_gameconfig`, and rejects overlap with another reviewed-width object. Exact reviewed field anchors can separately authorize a field offset. Access width alone never grants an object extent.

The 256 indexed `_g_ascii_props` bytes have a separate pinned declaration and oracle-byte proof; the following byte is checked as padding and grants no index 256. `_audiodriverstring` is a five-byte reference span. `smouspriteptr`, `mmouspriteptr`, and `mouseunkspriteptr` are each one four-byte `dd` declaration in the pinned reference, so their second words are bounded fields of the same pointer instead of separate global allocations.

The reviewed function overlay now checks the complete original table words and bounded destinations for the listed generic switch bodies, including the four draw-line selector tables whose zero/one prefix words are retained but excluded by the reviewed selector domain. Two exact unreachable post-table jumps in `track_setup` and `loop_game` are checked as code bytes and in-function branches, not discarded as padding. The conditional boundary rows with unresolved non-NOP ownership or missing entry anchors remain outside the overlay.

`tools/data_extent_generator.py` scans the locked image and instruction-verified function inventory for a constant scale of an index loaded from the same memory location tested by two dominating bounds. Both bad branches must bypass the indexed access. It normalizes field displacements within a stride, unions bounded witnesses, and rejects storage-boundary crossings, incompatible scales, interior independently anchored symbols, and unbounded indexed displacements within the proposed span. A compact `generated_extent` records the source base, stride, inclusive index bound, field offsets, and access sites; the resolver reruns the scan against the oracle before granting addends. The generated scan also accepts a corroborated ring-buffer extent when an original stride multiplied by a same-index wrap constant equals the exact pinned reference label span, every original write to the index is a constant initialization or guarded wrap, and no other symbol overlaps. For `audio_carstate`, 34 x 40 equals the 1,360-byte `_unk_44F4C` span at DS:`0x97DC`; the complete original index reference/write set, zero initialization, post-access wrap, pinned reference identity, and overlap check are revalidated at binding. The post-access check alone grants no width.

A multi-function recipe names a group and lists every contiguous inventory member with its exact original extent, hash, and emitted public offset. This includes every MSC local CODE public, whose independently reviewed extent is recorded as a local member. One complete object replaces exactly that interval; internal self-relative near CALL fixups use the emitted target public and computed signed displacement, while external fixups use the existing strict binders. A group may subsume an accepted single-function owner only when the recipe lists that owner, its extent equals a group member, and its active source is freshly recompiled to the original bytes. Otherwise the group may replace only raw ownership. Full object declarations, ordered fixups and relocations, and fresh whole-image equality remain required.

A member observed inside a near-call closure can also be a standalone C contribution when its separately compiled complete object has no outgoing near-call dependency and passes the same strict single-function gates. A separately compiled member can still fail when its own OMF FIXUPP order cannot reproduce the original ordered relocation sequence. This ownership can later be subsumed by an exact group recipe. TU-owned `_DATA`, `CONST`, or `_BSS` stays with the source contribution that emits and owns it. The diagnostic TU workbench derives a candidate initialized-data base only when original CODE operands independently agree and the complete emitted segment bytes match that grounded image span; its report does not grant ownership.


An ASM recipe has `kind: asm`, the `masm510-game` profile (`toolchain/msc510-msdos/MASM.EXE`), explicit `assembler_flags: ["/Mx", "/I."]`, a tracked `asm/*.ASM` source, and an empty include closure. `INCLUDE`, `INCBIN`, and `ORG` are excluded from this self-contained profile. The pinned assembler reproduces bytes; it does not identify the historical assembler. The complete emitted OMF SEGDEF/GRPDEF/PUBDEF/EXTDEF declarations and ordered FIXUPPs must equal the recipe, including no-fixup objects. The existing binder and fresh whole-image gate apply to ASM, with bounded MASM source-segment-frame far CALLs, original-frame corroboration, and the reviewed CS sprite-table LEA offset mode. MASM same-segment near CALL FIXUPPs in a multi-routine module bind only to listed member publics. An ASM owner is `MATCHING_ASM`, its secondary data is `MATCHING_ASM_DATA`, and validation counts its bytes separately from C and pinned runtime. DOSBox-X independently reassembles every active ASM source and checks the same complete binding and relocation obligations.

A complete single C module may bind MSC same-segment `offset16` code-table words (switch tables) to its own segment: MSC stores the in-segment offset in the LEDATA word with a zero FIXUPP displacement, the frame is the module's own segment (F0) or target (F5), the offset must lie inside the module, and the recipe's original frame must place the whole module in one 64 KiB frame. Group recipes and self-relative forms remain excluded from this C rule.

MASM DGROUP `offset16` references may use F1 group or F2 external frames when the exact GRPDEF index names DGROUP, or the frame EXTDEF independently resolves inside the same checked DGROUP paragraph. The target still needs a reviewed data alias and bounded addend. Same-segment `_TEXT` `offset16` table entries bind only within the complete single or grouped ASM module; each target displacement must remain inside its owned code extent. A module's own `_TEXT` `base16` MOV DX immediate may coexist with external far CALLs when its original segment paragraph is checked against function evidence and every segment-word MZ relocation appears in the exact oracle order. The pinned DOSBox-X reassembly invokes these same binders. `preRender_helper2` has an additional narrow boundary proof: its pinned Restunts `PROC`/`ENDP` source span, adjacent mapped procedure boundaries, 247-byte oracle hash, and seg012 frame must all agree before promotion.

The reviewed `_main` alias ties CRT0's original relocated far CALL at load offset 118009 to the game's reviewed `ported_stuntsmain_` entry at load offset zero. The pinned CRT0 OMF EXTDEF/FIXUPP site is separately checked when that startup member is staged. The group runtime binder keeps that entry's own paragraph-zero frame. This entry proof does not place CRT0DAT's zero-length linker sections and does not grant startup ownership by itself.

Startup members use four further group-runtime forms, each reviewed per fixup and never derived from the member under test. An external 16-bit code offset (F0 `_TEXT` frame) must be listed in `external_code_offsets`, name a staged pinned `_TEXT` public, and sit in a `MOV r16,imm16`, a `MOV [disp16],imm16`, or a DGROUP word that is exactly a public of the same object. The LINK `/DOSSEG` symbols follow the pinned CRT0 declarations: `_end` is the start of class STACK, placed by the MZ header SS reservation, and `_edata` is the start of class BSS, placed after the accepted `dos\nmsghdr.asm` EPAD section, the last non-BSS section in its pinned SEGDEF order, rounded to the word alignment of `_BSS` over a zero, relocation-free gap. Each reviewed signed addend is listed. CRT0DAT's COMMON `CDATA` and its zero-length DATA-class sections (XIFB..XCFE) are placed backwards from the accepted `HDR` section start (the next DGROUP class) in CRT0DAT's pinned SEGDEF order, across exactly the listed pinned intervening contributions. Each intervening contribution must be a complete word-aligned far-pointer table from a hash-pinned library member. The only current one is `_cflush.asm` XP, 4 bytes. Each pointer must land on its verified inventory entry through an original relocated segment word, and the ordered MZ table must hold no other relocation in the placed span. The neighbour must be another owner already in the canonical manifest. The BSS-class XOB/XO/XOE sections have no independently grounded neighbour: the only operands naming DGROUP 0x72B4 are CRT0DAT's own, the end of the complete `_BSS` is raw, and LINK communal allocation is unsupported. They therefore fail closed, and CRT0DAT, and with it the startup SCC, remains raw.

A group runtime member may bind an exact far CALL (`pointer32`, zero addend) into raw runtime code through a reviewed far code alias listed in `code_aliases`. The alias must resolve through `layout/code-symbols.json` with its own original relocated CALL anchors and verified mapped entry in the runtime `_TEXT` frame. Once the provider is owned, its pinned public must agree with the alias. `_write` and `_fflush` are reviewed runtime aliases whose spelling equals the inventory's runtime public name. The code-pointer-only binder permits the specific `remove_frame_callback` object to bind its original MOV AX offset / MOV DX segment pair and far CALLs without inventing a DGROUP field.

Runtime members are matched by pinned archive/member identities and complete extents. Fixup-bearing owners carry the complete ordered FIXUPP list, full segment/public/external declarations, exact original MZ relocations, and a `runtime-member-v1` or `runtime-owner-group-v2` binding. The group mode resolves staged pinned publics without recursive descent, then independently rebinds every member in the staged whole-image build; each referenced public is checked against its pinned source declarations and its addend stays within the declared object. Far CALL/JMP pointers use the original relocated `_TEXT` frame; reviewed internal far CALLs and code-offset instructions have their own narrow source-site checks. DATA offsets use independently anchored DGROUP aliases, complete pinned CRT0DAT `_DATA`/`CDATA` public extents, or the exact pinned `_file.c` DATA/COMDEF record. The latter remains raw-owned: its complete 282-byte initialized DATA, three ordered fixups, three disjoint 512-byte COMMON buffers, and original zeroing bounds are rechecked, while production still rejects a COMDEF-bearing owner object. Segment-local targets use the full declared segment and checked displacement. The single `HDR+8` end pointer in `dos\nmsghdr.asm` is checked against the immediately following MSG contribution and its original `MOV SI` operand. Some complete secondary DATA remains explicitly raw-owned: each such interval has a grounded placement, all of its bytes and fixups are verified on every build, and later source promotions cannot consume it silently. The MSG PAD/EPAD COMMON writes are replayed from all five exact pinned source members in original order and checked against the final image. BSS needs an independently verified range and a complete declared extent. Unsupported fixup shapes fail closed.

Default overlapping LEDATA remains rejected. Specific owners carry a reviewed `pinned-ordered-ledata-v1` policy with exact record offsets, payload hashes and overlap sites. Overlapping writes covering a fixup must agree byte-for-byte with each other and the merged field. Bounded LIDATA16 is expanded and checked in full; a FIXUPP over iterated data remains unsupported. Exact sparse-zero policies preserve the declared segment length and every initialized range. The one CRT0 COMMENT checksum allowance requires the exact pinned member hash, record offset, record type, OMF length, body hash, and original checksum byte; the record is retained unchanged. This allowance does not confer CRT0 ownership. The two known CRT absolute marker publics are accepted only at their exact sentinel value and do not bind code or data. The separate pinned `dos\diffhlp.asm` member declares `__AHSHIFT` as absolute word 12; its only supported use is a zero-addend `loader-offset16` MOV CX immediate, corroborated by the original `B9 0C 00` at load offset 28768 without an MZ relocation. Untouched historical LINK fixtures test ordered LEDATA policies with both pinned compiler distributions. No global checksum or overlap exception exists.

Literal C includes are resolved before compilation: angle headers come only from the hash-pinned profile INCLUDE directory, and quoted headers come only from tracked `include/` files. Search records each included path and SHA-256 in its frozen environment; recipes freeze the same closure, and strict acceptance and DOSBox-X independently verify it. The historical `#pragma pack(1)`, `pack(2)`, `pack(4)`, and `pack()` forms pass through unchanged and are recorded with their source location and value in that closure. The pinned MSC 5.10 `#pragma intrinsic(...)` and `#pragma function(...)` forms are allowed for the verified I/O and interrupt names `inp`, `outp`, `inpw`, `outpw`, `_enable`, and `_disable`, plus the floating-point intrinsic names listed in the pinned MSC 5.10 `README.DOC`; their ordered names and source locations are frozen in the same closure. Other pragmas and names are rejected. Sources without includes or supported pragmas have an empty closure.

The compiler profile is a compatibility hypothesis: Microsoft C 5.10 medium model with `/O /Gs` is pinned, but matching code under 5.00 prevents a unique historical version claim. Original TU grouping, general linking, arbitrary segment/frame modes, QuickC BAKPAT, local communal records, and unreviewed CS-relative storage remain technical work. Search can inspect unsupported objects and context hypotheses without weakening production.

Complete ASM modules may bind direct CS memory operands only to the reviewed sprite or interpolation data extents, with a CS override, a complete displacement field, and an in-object addend. A local far CALL or JMP may target an interior label only in one complete module with its original CODE frame and exact MZ segment-word relocation. Multi-function promotion may subsume a previously accepted group only when every ordered member identity is retained in one contiguous slice and that entire accepted group freshly verifies. Ordered MZ relocation sites must follow the candidate object's own FIXUPP and CODE record structure. The CODE cut simulator applies the validated MSC 5.10 record rule. A CODE LEDATA record closes after the emission unit that brings it to at least 944 bytes, or after the unit carrying its 99th FIXUPP; observed records hold at most 949 bytes. A `jcc $+3` followed by a near JMP is one unit, and each switch-table word is one unit. Regression tests compile accepted recipes and bounded probes with the pinned compiler, then compare the rule against their observed OMF records. Observed LEDATA ends remain the exact diagnostic, and the simulator reports every record that disagrees with the rule. It is diagnostic only and never supplies relocation order.

`--verify-only` for C, ASM and runtime candidates does not take the exclusive writer lock. It reads canonical inputs under a publication sequence number that each publisher makes odd before journaling or writing and even only after its journal is gone; a check that starts during a publication, or observes a changed sequence number, journal, or canonical input identity, reports a retryable snapshot change and never a verification result. Publication itself keeps the exclusive lock, journal, and rollback. Promotion preserves all existing owner intervals except the explicitly listed, freshly reverified owners subsumed by a multi-function contribution. A new single function or complete pinned runtime member can replace only a wholly raw interval. Runtime publication uses `promote_runtime.py` and the same exclusive lock, staged whole-image build, journal, input snapshot, canonical whole-image build, and rollback path as C promotion. Replacing an accepted function requires the same interval and fresh exact output. Canonical input identities are checked before and throughout serialized publication. Scratch histories are outside acceptance inputs.

Full validation combines negative technical tests, fresh pinned C compilation, runtime binding, complete hybrid image and ordered relocation equality, and independent DOSBox-X recompilation. Reports are derived under `build/validation/` and `build/exact/`. Source hashes, object bytes, and every binding are checked anew; historical receipts cannot authorize acceptance.
# Data-only modules

A `data_only` recipe identifies a complete C or ASM OMF module with zero CODE length, full segment declarations, publics, externals, LEDATA, and ordered FIXUPPs. Its complete initialized `_DATA` extent is a standalone `MATCHING_C_DATA` or `MATCHING_ASM_DATA` owner. C is the default classification because the image does not distinguish C from MASM data; ASM requires positive evidence. The hybrid placement gate uses unrelocated original CODE operand words, including raw CODE, to ground one module base and checks every recorded public/alias offset against it. Native LINK slot uniqueness and a full normal LINK image remain final closure work.

Every offset16 pointer FIXUPP is bound to a complete in-module public object or independently grounded external DGROUP object, with its addend inside that object and its two bound bytes exact in the oracle. The binder rejects other emitted nonempty segments, unexpected fixups, extra bytes, moved publics, and module boundaries that break MSC word alignment. A larger exact module may subsume complete accepted data owners through an explicit `subsumed_data_owners` list; previously accepted code and all other owners remain independently recompiled. The whole staged image and ordered MZ relocations must still match. The independent DOSBox-X crosscheck recompiles every active standalone data module.
# Per-object flags, whole ASM modules and far data (integ24)

The canonical C profile stays `/AM /O /Gs`. A C recipe may carry a reviewed `compiler_flags` set, with its `compiler_flags_register` id, only when every function it contributes belongs to one object named by a SUPPORTED `TUFLAG-*` register entry and the flags equal that entry's ruled set (`tools/object_flags.py`: `/AM /Oa /Gs` for seg014, seg015, seg019 and seg021-seg025; `/AM /Ox /Gs` for seg027 and seg030). The register is re-read on every use; a status, scope or ruling change refuses the override. The set applies to the whole object: every canonical-flag C contribution inside a flagged object must emit the identical complete object under the object's set as well, on every build and in the DOSBox-X crosscheck. Flag sets are reproduction profiles, not provenance claims.

A whole-module ASM recipe (`module_proof`, kind `asm-module-extent-v1`) covers one complete assembled module as one contribution. Both ends are rechecked from the oracle: a zero fill byte after an unconditional transfer (outside the module, or as the module's own terminal byte when an accepted owner already holds it), or a verified neighbouring function in another code frame. Every public entry lands on an inventory-verified start in the module frame; an entry whose inventory row is only partially mapped needs original relocated far CALLs from instruction-verified callers outside the module. A labelled data table inside a verified module procedure may be a declared embedded public. Procedure ends and internal labels are not required individually; a verified procedure may not cross either module end, and an inventory row may run past the end only by the one clipped fill byte. Declarations, ordered FIXUPPs, bytes, ordered MZ relocations and fresh whole-image equality remain mandatory. A module may subsume accepted ASM owners that start at its entries and end at an entry, a verified function end or the module end, each freshly reproduced.

Only such a grounded module may subsume an accepted C owner inside it. The C owner is reclassified MATCHING_ASM and its source retired from ownership (recorded as `reclassified_owners`) when a same-module link is rechecked: an odd start without a pad byte (MSC word-aligns every function), an original rel8 branch crossing the owner boundary, or membership of the module's shared ASM code frame strictly inside a zero-fill-bounded module with no fill at either owner edge. Ordinary groups still cannot cross kinds.

MASM 5.10 keeps 31 significant characters of a name. An ASM member or module public may be the truncated spelling of its longer inventory name; far-code and data aliases accept a truncated spelling only when marked `masm_truncated_public`, and still resolve the full inventory entry or pinned label.

A far-data module (`data_only` plus `far_data`) is one complete paragraph-aligned FAR_DATA segment with no FIXUPPs and publics whose declared sizes cover it. Its placement needs at least one original relocated segment word whose paragraph equals the module start: an immediate in an instruction-verified procedure, or a DGROUP word declared `dw seg X` at its placed pinned label. Optional offset anchors tie public offsets. C is the default classification.

Per-fixup composition also covers reviewed CS-island data: an adjacent MOV AX offset / MOV DX segment pair beside far CALLs and DGROUP offsets, and CS-override memory operands in composed ASM modules. The reviewed CS operand forms add `MOV Sreg,mem`, `ADD r16,mem` and `IDIV mem`. Generic CS islands (for example the 256-byte `incnums` table) are rechecked from their pinned `db` listing, label placement, width and one original unrelocated operand in a verified procedure of the same frame. External far JMP thunks (`EA`) bind like far CALLs, and a relocated far JMP anchor grounds a code alias like a far CALL. An emission-verified entry bounded on both sides by instruction-verified neighbours may ground a code alias or a single ASM recipe when marked `verified-neighbours-v1`.

A 4-byte `dd` object whose pinned single-declaration span is placed at the alias address, and which original code accesses as a far pointer (LES/LDS or its +2 word), has width 4, so segment-half addends are in-object. A placement-checked label with a reviewed width may be anchored by an original access to an element inside its extent (`field_offset`). Data aliases whose spelling named a label placed elsewhere in the pinned reference were corrected: the address keeps the label actually placed there (or its existing address alias), and the old spelling is re-derived at its own placed label with an original anchor; each change is listed in `renamed_aliases`.

Pinned toolchain files keep their logical `toolchain/...` identities; a profile's `directory` may name a hash-identical copy elsewhere (`logical_directory` maps the logical paths). The independent crosscheck runs the hash-identical DOSBox-X copy at `C:/tools/dosbox-x/dosbox-x.exe`.
