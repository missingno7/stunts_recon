# Endurance-001 handoff

## Scope and counts

The frozen purposeful sample covered 10 research routines plus two exact controls. The routine batch used 10 hypothesis compiler processes across 13 short-budget rounds and made one strict promotion (`toupper`). The Luna/high isolated cohort used 31 actual compiler processes: 21 produced effective output identities not seen earlier in their case histories, eight reproduced a known effective output, and two named-segment syntax tests were compiler-rejected before object emission. Three compiled objects across two cases contain Microsoft OMF B4/LEXTDEF records. The strict production reader rejects B4; the existing generic `OmfReader` parsed these objects and the frozen diagnostic engine then generated full diagnostics in isolated research. No production parser behavior changed. No endurance candidate was promoted. One precompiler/harness failure each on `mmgr_copy_paras` and `file_load_shape2d_nofatal` is separate and does not count as a compiler process. Total hypothesis compiler processes: 10 + 31 = 41 / 50. Three reallocations moved unused slots from `parse_shape2d_helper` and `is_facing_camera` to nofatal and the based-segment test after documented convergence/new object evidence; the case-cap sum remains 34, leaving three per-case slots unused plus six globally unallocated/reserved.

Meaningful-hypothesis outcomes by per-case index band (not a global rank): 1–3: 16 trials, 14 new effective output identities, one repeat, one compiler syntax rejection; 4–6: 13 trials, five new identities, seven repeats, one compiler syntax rejection; 7–10: two trials, two new identities; 11+: none. Of eight output repeats, five were deliberate cross-profile checks (same source under MSC 5.0 versus 5.10); three were source-level convergence repeats that tested already-ineffective local changes (signed-char return, register formal, repeated expression form). A new identity means a distinct effective code/fixup/context result; source-text changes and profile repeats are not counted as new effective outcomes. No matched Astra-from-start cohort exists and no Astra-token savings are estimated. Parent accounting and published API-equivalent scenarios are archived in `recovery/corpus/batch-001/usage.json`; root is refreshing them after final cohort accounting. These are not Codex invoice amounts.

Root reports fresh whole-image validation at 134 tests, 11 independent functions, `HYBRID_EXACT`; endurance candidates were excluded. Two promoted exact cases (`audioresource_get_dword`, `nopsub_26552`) were carried as controls and were not recompiled to pad the cohort.

## Established facts and next discriminating questions

The endurance step produced useful narrowing beyond three attempts, but no new strict promotion. It demonstrated that repeat outputs can be recognized and analysis can move from local syntax to compiler version, flag, ABI, register lifetime and symbol/fixup evidence. It did not establish a general task solvability rate or infer a Luna capability ceiling.

Material follow-ups are narrow: recover caller/TU/declaration evidence for camera and shape-count;  establish original source/profile context for `mmgr_copy_paras` and `parse_shape2d_helper`; recover original source-width/TU context for RPM; obtain mapped data and adjacent-function link context for `mmgr_get_chunk_size`; provide strict production parsing for B4 LEXTDEF/B6 LPUBDEF with local-vs-global visibility preserved if static functions are needed for acceptance. The generic research reader already parses these records; broader linking is outside this cohort. The `rect_adjust` case needs caller/register-lifetime evidence before another source trial. The repeated friction was two precompiler harness errors and the strict object reader’s rejection of Microsoft C static-symbol records (B4/B6). Microsoft documents these as local symbols for C 5.00/5.10 ([OMF extensions KB Q28613](https://jeffpar.github.io/kbarchive/kb/028/Q28613/)); repo `tools/omf.py` already parses them for isolated research. Separately, the [Microsoft C 6.0 programming manual](https://bitsavers.trailing-edge.com/pdf/microsoft/msdos_c/Microsoft_C_6.0_1989/LN06514-1189_Microsoft_C_Advanced_Programming_Techniques_198911.pdf) documents `_based`/`_segname` as C6 features; both spellings were rejected by pinned C5.10. Keep these as tooling/profile boundaries, not model failures. No diagnostic, compiler, acceptance or binding tool was changed.

Candidate and generated binary artifacts remain ignored locally; no generated/reference binary is included in the handoff.
