The first two use `tools/prepare_far_call_candidate.py`. It accepts only an existing raw-owned verified interval and fresh pinned compiler output with one full `UNIT_TEXT` public, zero extra segment contributions, complete declarations and ordered fixups in the historical-LINK-tested `external-far-call-v1` subset. It resolves target addresses from independent original relocated caller anchors in `layout/code-symbols.json`, checks ordered original MZ relocation sites, requires the bound whole contribution to equal pristine bytes, and records a straight-line CFG overlay with exact boundary anchors. It prepares source/recipe/evidence; it does not promote. Unsupported objects or differing extent/bytes fail closed.

## Direct-flow and multi-call follow-up

Five Luna/high family batches sampled 15 current SUPERVISOR functions with six frozen hypotheses and at most six compiler processes per family (30 compiler processes total). The full plans, candidate objects, diagnostics, and falsifiers are archived in `build/private/research-batches/`. This is a desktop research cohort; no model-weighted cost was recorded, so process counts must not be treated as cost comparisons. Each output remained research-only until independently prepared and promoted by the single writer.

The preparation helper now closes bounded direct branch flow, including loops and unreachable NOP padding, through the independent `function_evidence.py` traversal. It still rejects indirect control flow and non-far calls. It compares pristine CALL sites as a set against complete compiler FIXUPP sites; the binder retains the original OMF order and original MZ relocation-table order. This matters for `file_combine_and_find`, whose two FIXUPP records and MZ entries are both in descending address order while the mapped interval lists sites in ascending order. No relocation order was normalized for acceptance.
